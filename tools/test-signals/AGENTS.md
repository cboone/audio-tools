# Exact test signals

Read `README.md` first. It carries the problem statement, the usage, the four decisions that shape the output, how the readback verification works and why it is split in two, the worked example this tool was adopted from, and the known limitations.

The readback is the point of the tool, not a convenience on top of it. A generator that silently clipped its own output would produce a level sweep that tested nothing, and every number measured with it would be a claim about a file nobody checked.

## Notes for agents

- **Do not collapse the two verification checks back into one tolerance.** Comparing the file's peaks against the in-memory array's peaks is exact and catches a bad write. Comparing the in-memory peak against the requested level is a different question whose honest answer depends on the waveform and the frequency. The bash script this replaces conflated them at 0.0005, which passed only because every frequency it shipped happens to land a sample on the crest at 48 kHz; at 16 kHz against 48 kHz a correct sine peaks 13.40% low. One tolerance cannot be both exact enough to catch a clipped write and loose enough to accept a correct file. Note that landing on the crest is not the same as dividing the sample rate, which is how this was first written and it was wrong: a sample hits the crest exactly when `sr / (4 * f)` in lowest terms has an odd denominator, and 1600 Hz divides 48 kHz exactly 30 times yet still peaks 0.55% low.
- **Do not tighten the floors.** `sine_floor`, `saw_floor` and `gated_floor` are worst-case bounds over phase, not estimates of what a given file will actually reach. A long file usually lands far closer to the crest than the bound allows. Making them tight would start rejecting correct files, which is the failure the split was introduced to fix. `sine_floor` and `gated_floor` also return zero when there is no crest in range, which is a second version of the same rule: the phase bound assumes the signal gets to a crest at all, and `--seconds 0.001` at 100 Hz covers a tenth of a turn and reaches 0.577 of its amplitude, correctly, which at the default `--sine-level 0.5` prints as a peak of 0.288573. Do not "restore" the bound there. The shortfall is still printed, so a file that short is loud about it rather than silently blessed.
- **Do not add a flag to skip verification.** Every file is checked, unconditionally, and there is nothing to trade off: the check costs one read of a file that was just written.
- **`--levels` and `--saws` take strings, not floats, and that is deliberate.** The filename is made from the literal token the caller typed. Parsing them as floats gives `level-0.01.wav` for `0.010` and `saw-0.9.wav` for `0.900`, which silently renames the files a caller's own procedure refers to by name.
- **Do not fade these signals.** `tools/sampler-nulltest/maketest.py` fades because an abrupt start is broadband content that would contaminate a transfer-function measurement. Here the requirement is the opposite: the file must hold an exact peak for its whole length, and a fade would make the level check depend on where the peak happened to land. The two tools disagree on purpose.
- **The Fósforo levels are not defaults and must not become defaults.** `1.050` and `1.089` bracket `trace_rail / trace_full_scale` from one plugin's `src/gpu/iface.zig`. Any other instrument has a different threshold, or none. They belong on the command line, and `README.md` shows the invocation.
- **The screenshot analyzer is not coming here.** Issue [#1](https://github.com/cboone/audio-tools/issues/1) floated adopting `measure-trace` alongside the generator. [cboone/fosforo#64](https://github.com/cboone/fosforo/issues/64) settled that it stays in that repository, and the reasoning holds: it restates `trace_full_scale`, `trace_rail` and two shader color literals that it does not own, it cannot measure any other oscilloscope, and its only real safeguard is a test that reads the script and checks those constants against the Zig source, which can only exist there. The admission criterion this repository states for itself is that the _analysis_ be general; that one is a display contract restated in Python.
- **There is no test suite.** Validate any change by rendering and checking the result, and by proving the verification still fails when it should. The cases used so far: render the full default set and confirm 18 files with the expected peaks; render with fosforo's parameters, which add two levels and so make 20 files, and compare every one against `~/Music/fosforo-test-tones`, which the original ffmpeg script produced and which the port currently reproduces bit-identically; read `level-2.000.wav` back and confirm WAV format tag 3, 32 bits, and samples above unity; render a frequency whose crest falls between samples, such as 16 kHz or 1600 Hz against 48 kHz, and confirm the shortfall is reported rather than failed; render above Nyquist and confirm it is refused. Then inject each of these faults into a copy and confirm each exits 1: writing `int16`, clamping to unity, rendering `pan-hard-right` into both channels, and rendering a level louder than requested.
- **Output is not committed here**, unlike `tools/sampler-nulltest/probe/*.wav`. Those are fixtures that real bounces were made from and that the analysis compares against. These are 18 files at the defaults, roughly 7.7 MB each, that nothing compares against and that regenerate in seconds, so `.gitignore` carries `tools/test-signals/*.wav` instead. That entry only reaches output written into the tool's own directory, and `--outdir` defaults to the current directory, so a run started from the repository root drops 18 large untracked files in the root. Pass `--outdir`.
- The script carries PEP 723 inline metadata and a `uv run --script` shebang, so `uv run maketones.py` or `./maketones.py` needs no environment setup. System `python3` has no `scipy`, so plain `python3 maketones.py` will fail.
- Frequencies are refused at or above Nyquist rather than allowed to alias. An aliased sine is silently not the signal its filename claims, which is worse than an error, and the filename is what a procedure written against these files refers to.
- **Every float the caller can set is validated at the boundary, and the finiteness test is not decoration.** NaN is false against every comparison, so a bare range check passes it: `--seconds nan` cleared `seconds <= 0.0` and surfaced much later as a traceback from `int(sr * nan)`. The rates are worse, because `--click-rate 0` reached a division by zero inside `gate()` and a negative rate held the gate open for the entire file without complaining. Keep `math.isfinite` in front of the range test when adding a flag. A pair of individually valid values can also combine into nothing, which is why `--sr` and `--seconds` are checked again as a product: `1e-6` seconds at 48 kHz is finite and above zero and still rounds to no samples, and the empty array surfaces as `zero-size array to reduction operation maximum` out of `peaks()`. Levels are the one group allowed to be zero, since a file of digital silence is a legitimate thing to ask a display for and `render()` already reads correctly when the requested peak is zero.
- **A gate's open time is refused once it reaches its own period**, because `(t % period) < open` is then true everywhere and the file is a continuous tone under a name promising a click or a burst. `--click-ms 500 --click-rate 2` was the case: a 500 ms period filled by a 500 ms gate, rendering an ungated 1 kHz sine into `click-2hz.wav`. Nothing downstream catches it, since the peak is exactly what was asked for, so the check has to be at the boundary. This is the Nyquist rule in another dimension: a file must not quietly be a different signal from the one its name states.
- `timeline()` rounds rather than truncates. `sr * seconds` is a binary float that lands just under the whole number for some ordinary inputs, and `44100 * 0.7` is `30869.999999999996`, so `int()` gave a file one sample short of the length asked for. `tools/sampler-nulltest/maketest.py` still truncates; that is a difference between the two, not an inconsistency to iron out here.

## Status

The tool is adopted, parameterized and validated. It reproduces the signal set it came from bit-identically, and the verification has been seen to fail on four injected faults rather than merely assumed to work.

Remaining work is in the other repository and is tracked as [cboone/fosforo#67](https://github.com/cboone/fosforo/issues/67): that repo still carries `scripts/make-test-tones`, its `.editorconfig` still names the file in the shell brace list, and two plan documents in its `docs/plans/done/` reference the script by path. Those are historical records, so a pointer note is more appropriate there than a rewrite. Nothing in this repository blocks on it.

The obvious extension, if something needs it, is verifying frequency as well as peak. Nothing currently checks that a file rendered at 200 Hz is at 200 Hz, so a synthesis bug producing the right peak at the wrong frequency would pass. Counting periods on a display is the only thing that catches it today. Do not add it speculatively; add it when something needs it, and give it the same treatment as the level check, which is a bound that cannot reject a correct file.
